## Регистрация покупателей — на проде с 30.08.2026

Повод: **почты покупателя у нас не было нигде.** Заявка из корзины приносит имя, телефон,
страну и VIN; форма проверки — имя и телефон. Написать человеку о поступлении детали
было нечем, и весь накопленный спрос жил ровно до конца одного разговора в мессенджере.

**Вход и регистрация работают: Google и почта с паролем.** Страницы `/<язык>/auth`
и `/<язык>/account`, обе двуязычные и обе `noindex`. В шапке — «Войти», у вошедшего
«Кабинет». Провайдер входа стоит в `[lang]/layout.tsx` выше шапки.

**Пул аккаунтов общий с kmotors — решение владельца.** Вход идёт в тот же GoTrue боевой
базы, где у kmotors уже работают свои `/auth` и `/account`. Клиент kmotors войдёт к нам
своим аккаунтом и наоборот; площадки партнёрские, владелец один. Google в этом GoTrue
**уже включён** — в Google Cloud Console заводить нечего.

**Покупатели лежат в своей таблице `partsfit_customers`**, а не в `profiles` kmotors:
почта, имя, телефон, язык, способ входа, площадка первой встречи и согласие на рассылку.
Пишет её только сервер (`/api/auth/sync`) и только после проверки токена — почта берётся
из подтверждённого токена, а не из тела запроса.

**Сессия живёт в localStorage, а не в cookie.** Это не стилистика: cookie пришлось бы
читать на сервере, а обращение к запросу в layout переводит в динамику весь сайт.
Сборка после регистрации осталась прежней — ни один маршрут статики не потерял.

**Проверено локально целиком, на продовом поведении.** Локальный GoTrue переведён
в тот же режим, что прод (подтверждение почты обязательно), и путь пройден весь:
регистрация → письмо в Mailpit (`127.0.0.1:54324`) → ссылка → сессия → кабинет с именем
и телефоном, которые ждали в метаданных пользователя всё время между регистрацией
и подтверждением. Плюс вход паролем, выход, сторож кабинета и отказ API без токена (401).
**Google тоже проверен локально** (29.08.2026): в клиенте Google разрешён локальный
адрес возврата рядом с боевым, вход прошёл, строка в `partsfit_customers` легла
с `provider = google`, именем из аккаунта и пустым телефоном — Google его не отдаёт.
Клиент у нас с kmotors один и тот же, это выяснилось из публичного редиректа боевого
GoTrue. Команды и ловушки — в `AGENTS.md`, раздел «Как проверить вход локально».

### Что пришлось настроить на сервере — 30.08.2026

Код был готов накануне, а день ушёл на окружение. Ни одна из пяти находок не была видна
до выкатки, и каждая ломала регистрацию молча.

**1. Миграция** `20260829140000_partsfit_customers.sql` через SQL Editor — до деплоя кода.
Сделана. Плюс отдельной строкой `revoke all … from anon`: прод раздаёт новым таблицам
права анонимному ключу сам, в отличие от локального стека (подробности в `AGENTS.md`).

**2. Список разрешённых адресов возврата у GoTrue.** Был **пуст**, а `SITE_URL` — 
`https://www.kmotors.shop`. То есть любой возврат на наш домен GoTrue подменил бы
на kmotors, и это не выглядело бы ошибкой. Задаётся не там, где ищешь: в self-hosted
разделов URL Configuration и OAuth Apps в Studio нет вовсе, а в compose переменная
собирается из **`ADDITIONAL_REDIRECT_URLS`** — задать `GOTRUE_URI_ALLOW_LIST` напрямую
бесполезно, compose её перекроет. Сейчас там наши два домена и kmotors.

**3. Почта не была настроена никогда** — ни у нас, ни у kmotors: все `SMTP_*` пустые.
Подключён Resend, отправитель `noreply@kmotors.shop`, домен подтверждён в Resend,
DMARC добавлен в Cloudflare рядом с SPF и DKIM.

**Порт — 2587, и это не вкусовщина.** Хостинг режет исходящие 25, 465 и 587: GoTrue
висел на них ровно десять секунд и отваливался по таймауту без внятной ошибки.
У Resend для таких случаев есть 2465 и 2587; берём 2587, потому что на нём шифрование
включается после подключения (STARTTLS), а GoTrue именно так и делает для всех портов,
кроме 465.

**4. Свои письма** — `public/email/confirm.html` и `recovery.html`, по-английски
(решение владельца: письма общие на две площадки). Стандартный шаблон GoTrue отправился
в спам с первого же письма. Переменные `MAILER_TEMPLATES_*` и `MAILER_SUBJECTS_*`,
та же ловушка с именами, что в пункте 2.

**5. `SUPABASE_SERVICE_ROLE_KEY` на проде не был задан вовсе.** Сайт всё это время
работал анонимным ключом, и это годами не проявлялось: каталог анониму открыт, `leads` —
таблица общая с kmotors — тоже. Сломалось на первой нашей таблице, закрытой от анонима:
кабинет отвечал «не удалось сохранить», причина не была видна ниоткуда. Теперь ключ
задан, а роут `/api/auth/sync` проверяет его явно и называет переменную в ответе.

Про Google на проде: провайдер там включён давно, и клиент **тот же**, что у kmotors —
выяснилось из публичного редиректа их GoTrue. В Google Console пришлось добавить лишь
локальный адрес возврата для тестов; боевой `https://api.kmotors.shop/auth/v1/callback`
там был всегда, и наш домен Google не видит вовсе.

### Код из письма — второй путь подтверждения

Письмо GoTrue всегда предлагает шестизначный код рядом со ссылкой, а ввести его было
негде. Дыра при этом настоящая: **ссылка работает только в том браузере, где начали
регистрацию** — при PKCE секрет остаётся в его хранилище. Владелец на это и наступил,
открыв письмо в другом профиле Chrome. Экран «письмо отправлено» теперь принимает код,
и он проверяется на сервере, то есть работает с любого устройства.

## Прод и деплой: порядок, который обратного не терпит

**Код и база связаны.** Витрина читает `partsfit_*`; выкатить код на сервер раньше,
чем в боевой базе появятся таблицы, — значит положить раздел запчастей целиком.
Поэтому порядок такой:

```
1. миграции на VPS   supabase/migrations/*.sql через SQL Editor, по порядку имён
2. проверка          npm run partsfit:verify -- --prod
3. заливка           npm run partsfit:load   -- --prod
4. проверка ещё раз  npm run partsfit:verify -- --prod
5. и только теперь   деплой кода
```

Шаг 2 до заливки — не перестраховка: на локальном стеке мы уже ловили, что таблицы
из миграции не получают даже права на чтение, и на проде это выяснилось бы после того,
как 314 тысяч строк уже уехали. На пустой базе проверка сама переходит в режим «только
схема, права, ограничения и RLS» — содержательные проверки пропускаются с пометкой,
а не валятся кучей.

**Боевая база общая с kmotors** — 42 чужие таблицы в той же схеме. Поэтому только
SQL Editor: `supabase db push` и `supabase db reset` на прод не запускать никогда
(`reset` снёс бы kmotors целиком). Подробности и ловушка `parts_*` против `partsfit_*` —
в `AGENTS.md`.

Порядок проверен репетицией на локальной базе целиком: `db:reset` → `verify` (пустая,
схема и права зелёные) → `load` (10 с) → `verify` (35 проверок зелёные).

**Пройден на проде 26.08.2026 целиком, включая шаг 5.** Три миграции через
SQL Editor, проверка по пустой базе (схема, права, RLS), заливка 313 925 строк,
проверка ещё раз — 35 из 35. Расхождений
с локальным стеком не оказалось ни одного: гранты легли, ограничения ловят, аноним
читает все девять объектов и не пишет. Времена запросов с ноутбука — 300–900 мс против
2–12 мс локально; это круговая задержка до VPS, а не база: сайт живёт на том же хосте
и по сети не ходит. Проверить настоящие времена — на собранном проде.

Сборка перед выкаткой прошла без единой ошибки: 5 860 пререндеренных маршрутов,
из них 5 834 карточки, динамическими остались ровно четыре листинговых маршрута
и три API. Счётчик «Generating static pages» показывает при этом 8 035 — это его
внутренние единицы, а не маршруты; сверять надо по `.next/prerender-manifest.json`,
иначе расхождение читается как поломка.

**Что нужно на сервере.** Те же переменные, что и раньше, ничего нового:
`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`.

Оговорка про ключи: `createServerClient()` в `lib/supabase.ts` берёт `service_role`,
если он задан, и только иначе анонимный.

**30.08.2026 выяснилось, что на проде он не задан вовсе** — сайт всё это время работал
анонимным ключом. Не проявлялось потому, что каталог анониму открыт, а `leads` —
таблица общая с kmotors и тоже открыта. Сломалось на первой нашей таблице, закрытой
от анонима: кабинет отвечал «не удалось сохранить», и причина не была видна ниоткуда.
Значит, и обратное неверно: RLS на сервере **сработает**, и закрытая политикой часть
каталога ослепит витрину. Роут `/api/auth/sync` теперь требует ключ явно и падает
при загрузке модуля с именем переменной в сообщении.

**Чего на сервере быть не должно:** `.env.local`. Он локальный и перекрывает `.env` —
уехав на сервер, увёл бы прод на `127.0.0.1:54321`.

## Локальный стек между сессиями

```bash

```

`supabase stop` без `--no-backup` том сохраняет. Если база всё же потеряется,
восстановление — две команды: `npm run db:reset && npm run partsfit:load`, минута.

## Локальная база

```bash
npm run db:start        # поднять стек (Studio на http://127.0.0.1:54323)
npm run db:reset        # пересобрать базу с нуля из миграций
npm run partsfit:load   # залить каталог — 314 тыс. строк за ~11 секунд
npm run partsfit:verify # 24 проверки: ограничения, права, запросы, содержимое
npm run db:stop
```

**Всё по умолчанию идёт в локальную базу.** В `.env` лежат боевые ключи, в `.env.local` —
локальные, и второй перекрывает первый. Сверх того `scripts/partsfit/target.mjs` проверяет
адрес и на всё, что не localhost, требует явный `--prod`. Ошибиться молча нельзя.

Проверка не просто считает строки — она намеренно делает то, что **обязано упасть**:
дубль адреса, экземпляр без детали, запись анонимным ключом. Плюс замеряет запросы
витрины и сверяет содержимое. Если что-то отвалится на проде, оно отвалится и здесь.

## Что сделано в интерфейсе

Магазин на сайте работал целиком и до переезда: 10 страниц, 15 компонентов, корзина,
оформление заказа, фильтры, поиск, галерея, цены по курсу ЦБ. Его не переписывали —
переподключили к новым данным и добавили то, чего в старой модели не было.

**Шаг 1. Типы и слой доступа.** `src/types/part.ts` разводит деталь и экземпляр,
`src/lib/shop/catalog.ts` читает Supabase теми же двенадцатью функциями — компоненты
не тронуты. Счётчики фильтра считает база представлениями `partsfit_brand_counts`
и `partsfit_model_counts`.

**Шаг 2. Категории и тексты.** Одиннадцать типов деталей в реестре `CATEGORIES`, пилюли
переехали под заголовок и переносятся на вторую строку, тексты раздела и сайта больше
не обещают одну оптику. Хлебные крошки появились на категории, марке и модели — до этого
их там не было вовсе.

**Шаг 3. Карточка со списком экземпляров.** `components/shop/offer-picker.tsx`:
на детали с 64 экземплярами покупатель выбирает конкретный, и вместе с выбором
переключаются цена, галерея, состояние, разъём, цвет и VIN. В корзину уезжает выбранный
экземпляр, а не деталь.

**Шаг 4. Страница артикула.** `/zapchasti/oem/<номер>` — на каких машинах встречается
номер и что есть в наличии, с поиском и по кросс-номерам.

**Главная.** Вход в каталог: поиск по артикулу в герое, типы деталей, свежие поступления,
марки. Проверка по VIN осталась блоками ниже.

**Аналитика раздела — с 28.08.2026.** Счётчики (GA4, Метрика, Clarity) стояли давно,
но из магазина не уходило ни одного события: был виден трафик и не был виден путь.
Теперь идут четыре стандартных события GA4 — `view_item`, `add_to_cart`,
`begin_checkout`, `generate_lead`. Цена в них не передаётся, это решение владельца.
Значения `lead_source` совпадают с `source_page` в таблице `leads`, и сходиться они
должны до штуки — это единственный способ проверить, что счётчик не врёт.

**Шаг 5. Заливка в прод — сделан 26.08.2026.** Порядок и подробности выше, в разделе
про деплой. Схема с тех пор не менялась: правки 28.08 кода не касаются базы вовсе,
и деплой у них в один шаг.

**Английский, доллар и новая форма — 28.08.2026.** Раздел двуязычен целиком, включая
корзину и оферту; переключатель языка `LocaleToggle` стоит в шапке везде, кроме страницы
проверки по VIN — там свой, на три языка.

## Сколько страниц публиковать

Всего в базе получается **18 655 карточек** плюс 2 180 посадочных. Это перебор по двум
причинам сразу, и обе надо развести:

**Сборка.** До переезда было 994 страницы статикой за 9 секунд. ISR в Next 16 есть
(`node_modules/next/dist/docs/01-app/02-guides/incremental-static-regeneration.md`):
`generateStaticParams` отдаёт подмножество, остальное рендерится по первому запросу
и кэшируется. Оговорки оттуда: нужен Node-рантайм (у нас `output: standalone` — есть),
файловый кэш свой у каждого инстанса, наблюдать через заголовок `x-nextjs-cache`.
Вышло 5 860 страниц за 2,5–5 минут: пререндерятся посадочные и карточки с двумя
и более экземплярами, остальные рендерятся по первому запросу.

**Индексация.** В Search Console 307 755 адресов «обнаружена, не проиндексирована».
Добавить туда 18 тысяч — значит утопить их в том же хвосте.

И главное: **12 821 карточка (69%) держится на одном экземпляре**. Продадут — страница
умрёт. Публиковать их в карту сайта значит заранее наплодить 404.

| экземпляров на странице | страниц |
|---|---|
| 1 — живёт до первой продажи | 12 821 |
| 2–4 | 4 692 |
| 5–9 | 836 |
| 10 и больше | 306 |

**Решено 25.08.2026, уточнено 28.08.2026:**

| что | сколько | в индекс |
|---|---|---|
| посадочные (категории, марки, модели) | 2 180 | да, пререндер |
| карточки с 2+ экземплярами | 5 834 | да, пререндер |
| карточки с одним экземпляром | 12 821 | **`noindex`**, вне карты сайта |
| страницы артикулов с совместимостью | 15 708 | **да, с 28.08.2026** |
| страницы артикулов без совместимости | 1 047 | **`noindex`**, вне карты сайта |

Карточка с одним экземпляром страницу всё равно получает — иначе товар нельзя положить
в корзину. Но `robots: { index: false }` в `generateMetadata` и отсутствие в `sitemap.ts`:
продалась — исчезла тихо, не оставив 404 в индексе. Признак — `offers_count = 1`.

**Страницы артикулов ждали расчистки индекса и не дождались:** решение владельца
от 28.08.2026 — ждать хвост можно бесконечно, а эти страницы самые ценные по трафику.
Опубликованы не все: у 1 047 артикулов нет строки в `partsfit_fitment` (у донора
расходится тип детали или сторона), показать «встречается на этих машинах» нечем,
и страница держится только на товаре — пропадёт товар, останется 404. То же правило,
что и у карточек с одним экземпляром. Список для карты сайта даёт
`getIndexableOemNumbers()` — он читает таблицу совместимости, то есть только выживших.

**Английские страницы в пререндер не идут.** `generateStaticParams` дочерних маршрутов
по-прежнему возвращает пустой список для не-`ru`: сборка осталась 5 860 маршрутов,
английское рендерится по первому запросу. Трафика на них пока нет, а пререндер
удвоил бы сборку.

## Команды

```bash
npm run partsfit:index    -- <группа>          # индекс по листингам
npm run partsfit:coverage -- <группа> --oem    # чего не хватает в словаре
npm run partsfit:details  -- <группа>          # карточки отобранного
npm run partsfit:tables   -- <группа> [ещё...] # таблицы под Supabase
npm run partsfit:terms                         # полнота английского словаря
npm run partsfit:load     -- --dry-run         # посчитать, ничего не отправляя
npm run partsfit:viewer                        # локальный просмотр данных

npm run db:start / db:reset / db:stop          # локальный Supabase
npm run partsfit:load     [-- --prod]          # заливка в базу
npm run partsfit:verify   [-- --prod]          # 35 проверок базы
```

`partsfit:terms` гонять после каждого `partsfit:tables`: новая группа донора приносит
новые термины, и без проверки они молча уедут на английские страницы по-русски —
сборка не упадёт, глазами это ловится только случайно.

Группы: `headlights`, `taillights`, `control-units`, `side-mirrors`, `bumpers`, `doors`,
`fenders`, `sensors`, `wheels`, `misc`, `donor_cars`. Список — в `scripts/partsfit/lib.mjs`.
