# Скрапер partsfit.co.kr

Донор — магазин б/у автозапчастей с корейских разборов на CAFE24. У него около
**110 тысяч позиций** в девяти группах; наш прежний каталог из 967 фонарей — меньше
процента от этого.

## Порядок работы с новой группой

```bash
npm run partsfit:index    -- headlights          # 1. индекс группы
npm run partsfit:coverage -- headlights --oem    # 2. чего не хватает в словаре
#                                                # 3. дописать dict/*.json
npm run partsfit:details  -- headlights          # 4. карточки отобранного
npm run partsfit:tables   -- headlights          # 5. таблицы под Supabase
npm run partsfit:load     -- --dry-run           # 6. заливка (без флага — в базу)
```

Таблицы собираются сразу по нескольким группам:
`npm run partsfit:tables -- headlights control-units side-mirrors`.

Шаг 3 не пропускать: незнакомый корейский термин в таблицы не попадает, и без словаря
группа соберётся наполовину. Отчёт сортирует непокрытое по числу позиций — сорок верхних
строк обычно закрывают больше товара, чем весь остальной хвост.

## Почему два прохода

В листинге донора уже лежит всё, по чему принимается решение о публикации: корейский
заголовок целиком (а в нём и партномер), цена и `product_no`. **48 товаров за один запрос.**

Значит индекс группы в 13 тысяч позиций стоит 273 запроса и полторы минуты, а карточки
тянутся только под отобранное. Обратный порядок — сначала выкачать все карточки, потом
отбирать — дороже в полсотни раз и даёт ровно тот же результат.

Повторный прогон индекса сливается с прежним файлом: `firstSeen` сохраняется, цена
и `lastSeen` обновляются. По этому же файлу видно новые поступления и ушедшие позиции.
Каталог протухает небыстро, но заметно: из 25 проверенных фар одна пропала за десять дней,
у одного фонаря из 40 цена упала с 44 000 до 36 000 вон.

## Что берётся откуда

| поле | источник |
|---|---|
| заголовок, цена, `product_no`, миниатюра | листинг |
| партномер (`부품번호`) | карточка, отдельное поле |
| VIN донорской машины (`차대번호`) | карточка, отдельное поле |
| состояние, число пинов, тип лампы, кросс-номера | карточка, `<meta name="description">` |
| галерея | карточка, `big` и `extra/big` |

**Описание берём из метатега, а не из тела страницы.** Тело рисует редактор CAFE24 уже
в браузере, а метатег отдаётся сервером. Прошлый скрап смотрел на страницу глазами через
браузер и остался без состояния у всех 383 фар — это та же самая ошибка.

Headless-браузер здесь не нужен нигде. Если появится соблазн его завести — сначала
проверить, нет ли нужного в метатегах: до сих пор было.

## Чего у донора нет

- **Веса и габаритов.** Полей нет вовсе, поэтому в оферте они остаются оценкой.
  Для фары это не мелочь: от веса считается доставка, и порог «море выгоднее авиа»
  на `dostavka-i-oplata` опирается именно на него.
- **Партномера у части позиций.** Проверено на 60 карточках без номера в заголовке:
  ни в поле `부품번호`, ни в описании его нет ни у одной. Восстановить неоткуда,
  такие позиции не публикуются.

## Ловушки, на которые уже наступали

- **Хвостовое число в заголовке — не остаток на складе, а номер лота.** У позиций
  с «1», «2», «4» остаток везде единица. Донор так разводит одинаковые детали с одной
  разборки. В `stock` его писать нельзя.
- **Номер, записанный группами через пробел, лотом не режется.** «A 167 906 85 07»
  (Mercedes) — это один номер целиком, а «7 387 225-04 1» (BMW) — номер и лот.
- **Бейдж «품절» лежит в вёрстке всегда** и прячется классом `displaynone`. Наличие
  строки не значит, что товар продан, — значит отсутствие класса на ней.
- **`DLR X` значит «ДХО нет», а не «ДХО есть».** Отрицания (`X`, `없음`, `무`) проверяются
  в `describe.mjs`; без этого карточка обещает то, чего в детали нет.
- **Год ищется как последний четырёхзначный токен перед типом детали.** Иначе у Пежо
  с числовыми моделями — 2008, 3008, 5008 — годом становится имя модели.
- **Данные из страницы обязаны отрываться от неё через JSON.** V8 хранит подстроку,
  полученную регуляркой, ссылкой на исходную строку: поле `description` в сорок знаков
  удерживает в памяти всю страницу — 185 КБ. На восемнадцати тысячах карточек это 3,9 ГБ
  и смерть процесса; ровно так первая версия и умерла. `.trim()` и `.replace()` не спасают —
  без совпадения они возвращают ту же самую строку.
- **Файл пишется после каждой пачки, а не в конце.** Первая версия писала один раз
  в конце и при падении унесла полчаса работы. Повторный запуск продолжает с места
  обрыва: уже снятые `productNo` пропускаются.
- **У блоков управления стороны нет** (`BMW 5시리즈 2021 ECU 5A149A601`), а у «모듈(유닛)»
  в скобках стоит слово «юнит», а не сторона. Отсюда признак `hasSide` у типа детали.

## Словари

`dict/brands.json`, `dict/models.json` — корейское написание в международное и кириллицу.
Латиница словаря не требует: донор пишет ею уже международные имена (BMW, SM5, G80, A6),
и заводить на них записи вида `{"en": "A6", "ru": []}` значило бы держать словарь,
который ничего не переводит.

`dict/part-types.json` — тип детали в категорию сайта и русские тексты. Одна запись
на тип, отсюда же берётся род для согласования: «фара передняя левая», но «фонарь задний левый».

`dict/condition.json`, `dict/attributes.json` — разбор описания донора. Грейд ставится
**по худшему найденному маркеру**: «면상태최상» рядом с «파손» — это C, а не A+. Правило
одностороннее намеренно: пропущенный дефект стоит возврата, пропущенное достоинство — ничего.

Если описание есть, но ни один маркер не сработал — грейд `A+`, «дефектов не отмечено».
Если описания нет вовсе — грейд пустой, и карточка честно говорит «состояние не указано».
Ставить `A+` по умолчанию нельзя: это обещание, которого нам никто не давал.

## Деталь и экземпляр — разные сущности

Донор торгует разбором, и одна и та же деталь лежит у него в нескольких экземплярах
с разных машин. У левой фары Genesis G80 (`92101T1100`) их **шестьдесят три**: своя цена
от 198 до 385 тысяч вон, своё состояние, свои фотографии, свой VIN донорской машины.

Поэтому `products` — это страница детали (тип + марка + модель + сторона + позиция +
артикул), а `offers` — экземпляры на ней. По фарам это **3 161 страница на 7 271
экземпляр**. Сложить их в одну таблицу значило бы выкатить 4 110 почти одинаковых
адресов — при исчерпанном краулинговом бюджете (307 755 адресов в статусе «обнаружена,
не проиндексирована») именно так страницы в индекс и не попадают.

Фотографии принадлежат экземпляру, а не детали: покупатель смотрит на скол именно той
фары, которая ему приедет. Годы на странице — диапазон: одна деталь стоит на нескольких
модельных годах.

## Выход

| файл | строк по фарам | что это |
|---|---|---|
| `brands.json` | 38 | марки |
| `models.json` | 290 | модели |
| `part_types.json` | 1 | типы деталей |
| `products.json` | 3 161 | страницы деталей |
| `offers.json` | 7 271 | экземпляры |
| `offer_images.json` | 68 409 | фотографии |
| `fitment.json` | — | совместимость: артикул → машина |

Поля совпадают с колонками в миграции. Пока витрина читает JSON, это просто данные;
когда каталог переедет в Supabase, те же файлы заливаются без переделки. Префикс
`partsfit_` — чтобы вторая площадка в той же базе не столкнулась на `products`.

Порядок заливки: словари → `products` → `offers` → `offer_images`. Его соблюдает
`load-supabase.mjs` — внешние ключи ссылаются вверх по списку.

Заливка идёт через `upsert`, а не `insert`: повторный прогон скрапера обязан обновлять
цену и наличие, а не падать на дубликатах. Ключ нужен `service_role` — у таблиц включён
RLS, и анонимному разрешено только чтение.

264 тысячи строк уходят в базу примерно за 11 секунд пачками по 500 через PostgREST.
`COPY` через прямое подключение не понадобился.

## Совместимость

`fitment.json` и таблица `partsfit_fitment` выводятся из `products` при каждой сборке.
Своей жизни у них нет: правка руками исчезнет на следующем прогоне.

Строка означает **«донор продавал этот номер под этой машиной»**, а не «завод подтверждает
применимость». На витрине подписывать «встречается на этих машинах» — за формулировку
«подходит к» отвечаем мы.

В таблицу не идут артикулы, за которые ручаться нельзя:

| отсев | по трём группам |
|---|---|
| тип детали расходится (номер и блок комфорта, и блок АКПП) | 607 |
| сторона расходится (номер и слева, и справа) | 137 |
| модель неизвестна | 195 |

Что получилось: 14 669 строк на 13 981 артикул и 352 машины, **582 артикула встречаются
на нескольких машинах**. Данные проверяемые — `858914501` это общий ECU BMW 1/2/3 Series
и Mini, `03L907309` — дизельный блок VAG на Audi A4, VW CC и Passat.

## Локальная база

```bash
npm run db:start        # Supabase CLI: Postgres 15.8, как на VPS
npm run db:reset        # пересобрать с нуля из supabase/migrations/
npm run partsfit:load
npm run partsfit:verify # 20 проверок
```

**Всё по умолчанию идёт в локальную базу.** `target.mjs` сверяет хост и требует явного
`--prod` для всего, что не localhost. Это не перестраховка: в `.env` лежат боевые ключи,
а заливка пишет сотни тысяч строк.

`verify-db.mjs` намеренно делает то, что **обязано упасть** — вставляет дубль адреса,
экземпляр без детали, пробует писать анонимным ключом. Проверка, которая только считает
строки, пропустила бы ровно те беды, ради которых заводили локальный Supabase.

Две ловушки, пойманные на нём и записанные в `AGENTS.md`: права надо выдавать явным
`grant` (умолчания не дают даже `select`), а `major_version` в `config.toml` обязан
совпадать с продом.

Прогон детерминирован: на тех же входных файлах даёт байт в байт тот же результат
(проверяется сравнением md5 двух прогонов).

## Просмотр собранного

```bash
npm run partsfit:viewer      # http://localhost:4123
```

`viewer/` — инструмент разработчика, а не часть сайта. Читает таблицы, держит их в памяти
и отдаёт через маленький HTTP-слой: 83 МБ в страницу не вложить, поэтому фильтрация
и разбивка идут на сервере, в браузер уезжает только видимая страница.

Запросы в нём нарочно повторяют будущие запросы витрины — по типу детали, марке,
артикулу. Если что-то здесь неудобно выражается, значит неудобна схема: это первая
проверка модели на живых данных, до всякого Supabase.

Фотографий у детали с 63 экземплярами по восемь на каждый — 504 запроса на одно открытие
карточки. Поэтому в списке экземпляров показываются первые пять, остальные — по ссылке
у донора.
